# QA Testcase Personas — 7人の意地悪なQA

AIにテストケースを書かせると、放っておけば正常系に寄り、回帰・権限・異常データ・状態整合・仕様突合といった観点が毎回抜ける。原因はAIの能力ではなく「何を疑うべきか」を渡していないこと。このスキルは7人のQAペルソナを固定し、各ペルソナに最低1つずつ観点を出させることで、観点の網羅と品質の再現性を担保する。

## このスキルがやること / やらないこと

やること:
- 対象（機能 / PBI / コンポーネント / Figma / 仕様）から、7ペルソナ観点でテストケース表を生成する（テスト**設計**）。

やらないこと（明示的な責務分離。越権とでっち上げを抑えるため）:
- テストの**実行・合否判定はしない**。それは人間の仕事。AIは「テスト設計者」であって「テスター」ではない。
- **根拠のないケースを作らない**。一次情報（Test Basis）に紐づかない"それらしい"ケースは出さない。
- **コード/実装を確認できていない箇所を推測で埋めない**。分からないものは正直に「※要確認」と書く。

## 基本スタンス

「動いているはず」を信用しない。意地悪なくらい疑ってかかる。各ペルソナが最低1つは観点を残す。ロールは具体的に当てるほど指摘が具体的になる（「QAとして」より「不具合を見逃さない疑り深いシニアQAとして」、さらに7人に分ける）。

## ワークフロー

1. **一次情報（Test Basis）を確定する。** 何が正解の出どころか先に押さえる: PBI番号 / Figmaのフレーム / 仕様・ヘルプの見出し / 対象コンポーネント名。曖昧なら、推測で進めず「どれを一次情報にするか」をユーザーに一度だけ確認する。独自採番はしない。
2. **対象範囲を一言で確定する**（どの画面 / コンポーネント / フローか）。
3. **7ペルソナを順に当てる。** 各ペルソナ最低1観点。`references/qa-personas.md` を読み、各ペルソナの「具体的に何を疑うか」のチェック項目を使う。
4. **ISO 25010（9特性）で偏りを点検する。** 埋まっていない品質特性があれば、無理に水増しせず「E2E対象外 / 該当なし」と判断理由を一言添える。「網羅したつもり」を可視化するための物差し。
5. **各ケースに Test Basis（根拠）を必ず付ける。** 確認できない箇所は `※要確認（実装未確認）` `※要確認（仕様不足）` と正直に明記する。
6. **出力形式で表を生成する**（下記）。

## 出力形式（デフォルト: Markdownテーブル）

列はこの順で固定する:

`ケースID | ペルソナ | テスト観点 | 品質特性 | 優先度 | 前提条件 | 操作手順 | 期待結果 | 確認レイヤ | 回帰対象 | 自動化 | Test Basis`

- **ケースID**: `TC-<対象略号>-001` のような連番。
- **ペルソナ**: P1〜P7。どの視点から出たケースか必ず明示する。
- **品質特性**: ISO 25010 の特性名（機能適合性 / 使用性 / 信頼性 / セキュリティ / 性能効率性 / 互換性 / 保守性 / 移植性 / 安全性）。
- **優先度**: 高 / 中 / 低。
- **操作手順**: E2Eの手順を 1. 2. 3. と番号付きで。セル内改行は読みやすさ優先（Markdownなら改行、CSVなら`<br>`）。
- **期待結果**: 「画面にこう出る」だけで終わらせない。下の確認レイヤと整合させる。
- **確認レイヤ**: そのケースを**どこで確かめるか**。`UI表示` / `ネットワーク(リクエスト/レスポンス)` / `状態(store/cache)` / `URL` から該当を選ぶ。P4観点（画面を信用しない）を構造として強制する列。
- **回帰対象**: YES / NO。共通コンポーネントや既存挙動に波及しうるなら YES。
- **自動化**: `Playwright候補` / `手動`。網羅の段階ではどちらでもよいが、後で自動化を選別できるよう印を付ける。
- **Test Basis**: 一次情報への参照（PBI番号 / Figmaフレーム名 / 仕様の見出し）。無い/未確認なら `※要確認` と書く。空欄にしない。

件数が多い（目安15件超）/ スプレッドシート取り込みが必要、と分かっている場合は、**セミコロン区切り・セル内改行`<br>`・UTF-8** のCSVも併せて出す（タイトルや期待結果に「、」が入っても列がずれないため）。デフォルトは読みやすいMarkdownテーブル。

## 7人のQAペルソナ（サマリ）

詳細な「具体的に何を疑うか」と、そのまま貼れるプロンプトブロックは `references/qa-personas.md` にある。まずそれを読んでから観点を出すこと。

| #  | ペルソナ            | 疑う点（フロント/E2Eでの代表観点） |
| -- | ------------------- | ------------------------------------------------------ |
| P1 | 新人ユーザー        | 説明を読まず直感で操作。誤クリック・必須未入力での送信・連打（ダブルサブミット）・空状態での初見挙動 |
| P2 | パワーユーザー      | キーボード高速・大量入力。Tab遷移順・フォーカス管理（Dialog/Menu）・ショートカット・IME変換中のEnterで誤確定 |
| P3 | 悪意ある操作者      | 境界値・不正値・**権限外（認可境界 / 他社・他グループのデータ）**・二重送信・URL直叩き・hidden要素の強制操作 |
| P4 | 状態整合性監査役    | 画面の見た目を信用しない。裏側（API req/res・store/cache・URL）と一致するか。楽観的更新・キャッシュ無効化・"成功トーストは出たが永続化されていない" |
| P5 | 異常データ・限界状態 | 空・欠損・超長文・大量件数・絵文字/特殊文字・多言語・日付/TZ境界。empty/loading/error/部分失敗の表示、ページネーション境界 |
| P6 | 回帰デグレ番人      | 今まで動いていた周辺機能が壊れていないか。共通コンポーネントの波及・ブラウザ戻る/進む・リロード(F5)・レスポンシブ(画面幅)・複数タブ/アカウント |
| P7 | 仕様懐疑者          | 「実装＝正しい仕様」を信用しない。一次情報（PBI/Figma/仕様）と挙動を突合。Figma差分・受入条件・**アクセシビリティ要件**（ARIA/コントラスト/スクリーンリーダ）・i18n仕様 |

## 根拠のないケースを出させない（偽陽性を出さない）

テスト設計と同じで、いちばん大事なのは「それらしいが根拠のないケース」を出さないこと。

- **Test Basisに一次情報を引く。** 新機能ならPBI番号、仕様確認なら「どの見出しか」を節まで。独自採番はせず、既存の参照をそのまま引用する。
- **未確認は埋めない。** コード/実装を見ていない期待結果は推測で書かず `※要確認（実装未確認）` と書く。
- **テスト可否で仕分ける。** 「仕様がないから書けない」は隠さず、要件のギャップ（`テスト不可：仕様不足`）として可視化する。

## 品質特性（ISO/IEC 25010:2023, 9特性）

観点の偏りを見えるようにするための語彙。E2E/フロントで主に効くのは前半:

- **機能適合性** — 要件どおりの機能か（P7と相性）
- **使用性** — 操作性・分かりやすさ・**アクセシビリティ**（P1/P2/P7）
- **信頼性** — エラー時/部分失敗/リロード後の回復（P5/P6）
- **セキュリティ** — 認可境界・不正入力・権限外操作（P3）
- **性能効率性** — 大量件数・体感速度（P5）
- **互換性** — ブラウザ・画面幅・他機能との共存（P6）
- 保守性 / 移植性 / 安全性 — E2Eで直接当てにくいことが多い。該当しなければ「E2E対象外」と明記してよい（無理に埋めない）。
