# eng-split — Google Engineering Practices 準拠の作業分割（Small CLs）

Google の「Small CLs」ガイドラインに**厳密に準拠**して、要件や大きな作業を、小さく自己完結した複数の CL に分解し、依存関係とマージ順序を含む分割計画を作成するスキル。

## 正典（Source of Truth）

分割の判断基準は必ず以下のファイルに従うこと。開始時に**必ず該当セクションを読む**こと。

```
~/.claude/skills/_eng-practices-reference/google-eng-practices-verbatim.md
```

参照すべき主なセクション（原文の見出し）:
- `Small CLs` — 全体。特に以下のサブセクション:
  - `Why Write Small CLs?`
  - `What is Small?`
  - `Writing Small CLs Efficiently`
  - `Splitting CLs`（Horizontally / Vertically / 両方の組み合わせ）
  - `Separate Out Refactorings`
  - `Keep related test code in the same CL`
  - `Don't Break the Build`
  - `Can't Make it Small Enough`

## 実行フロー

### 1. 正典の読み込み

`google-eng-practices-verbatim.md` の `Small CLs` セクションを読む。特に以下を頭に入れる:

- **正しいサイズ = "one self-contained change"（1つの自己完結した変更）**:
  - 1つのことだけに取り組む（通常は機能全体ではなく機能の一部）。
  - レビュアーが必要以上の文脈を要求されない大きさ。
  - 変更の価値がレビュー・提出のコストに見合う。
  - システムの確立されたプラクティスに反していない。
- **小さいことの利点**: 速く・徹底的にレビューされる／バグが入りにくい／無駄になる作業が少ない／マージが容易／設計を磨きやすい／ブロックが少ない。
- **「小さすぎる」もありうる**: 1行追加でも他所に大きな影響があり、レビュアーが理解できないなら小さすぎる。
- **大きくてよい例外**: ファイル全体の削除（1行扱い）、信頼された自動リファクタリングツールの結果（検証だけでよい場合）。

### 2. 対象の把握

分割対象を特定する。

- **要件・仕様から分割する場合**: ユーザーから要件・仕様・設計を受け取り、実装範囲を理解する。不明点は分割前に質問する（CLAUDE.md のワークフロー方針）。
- **既存の大きな差分から分割する場合**: `git diff --stat` 等で変更範囲を把握する。生の diff の解析には context-mode の `ctx_execute` を使い要点だけ抽出するとよい。

### 3. 分割戦略の適用（Splitting CLs に準拠）

原文の分割手法を適用し、最適な切り口を選ぶ。

- **Splitting Horizontally（水平分割 / レイヤー単位）**:
  機能を、システムのレイヤー（Client / API / Service / Model 等）ごとの薄い変更に分割する。
- **Splitting Vertically（垂直分割 / 機能単位）**:
  コードをより小さなフルスタックの垂直機能に分割する。各機能は独立した並行実装トラックになりうる（あるトラックがレビュー待ちでも他を進められる）。一部の重複（共有スタイル・共有検証ロジック等）は許容。
- **Horizontally & Vertically（組み合わせ）**:
  両者を組み合わせ、各セルが独立した CL となる実装計画を立てる。モデル（最下層）からクライアント（上層）へ積み上げる。

各 CL について次を満たすか確認する:
- **Separate Out Refactorings** — リファクタリングは機能変更・バグ修正とは別 CL にする（ローカル変数名の修正等の小さな掃除は同梱可）。大きさはレビューを難しくするかで判断。
- **Keep related test code in the same CL** — 変更を検証する関連テストは同じ CL に含める（独立したテスト追加・テストのリファクタリングは別 CL でよい）。
- **Don't Break the Build** — 互いに依存する CL があるなら、各 CL を提出した後もシステム全体が動き続ける順序・方法を設計する（ビルドを壊さない）。

### 4. 分割計画の出力

分割計画を Markdown ファイルとして `/tmp` に出力する（CLAUDE.md の出力規約に準拠）。ファイル名は英語のケバブケース（例: `/tmp/eng-split-<topic>.md`）。

出力の構成:
1. **対象の概要** — 何を分割したか（要件 or 既存差分）。
2. **採用した分割戦略** — Horizontal / Vertical / 組み合わせ のどれを、なぜ選んだか。
3. **CL 一覧** — 各 CL について:
   - 連番・タイトル（後で CL 説明文の1行目になる命令文）
   - 含む変更（ファイル/レイヤー/機能）
   - **自己完結性チェック**: one self-contained change を満たすか
   - 含めるテスト
   - 依存する先行 CL
4. **マージ順序と依存グラフ** — Don't Break the Build を満たす提出順序。
5. **リファクタリングの分離** — 別 CL にしたリファクタリングと理由。
6. **注意点** — 小さすぎ/大きすぎの懸念、レビュアーへの読む順序の指針（Can't Make it Small Enough の場合）。

出力後、`mo` がインストールされていれば `mo <file>` で開く（`which mo` で確認。なければ通常出力にフォールバック）。

> 注: このスキルは**分割計画の作成まで**を行う。実際の実装やブランチ作成は行わない（必要なら計画をもとに別途依頼してもらう）。

## 重要な心構え（原文の核心）

- 巨大 CL を書いてから分割するのではなく、**最初から小さな CL の連なりとして計画する**（Writing Small CLs Efficiently）。
- 各 CL は **one self-contained change**。1つのことだけをする。
- ビルドを壊さない順序を必ず設計する。
- レビュアーは小ささを理由に CL を拒否する裁量を持つ。小さくする手間を惜しまない。
